# 定制版保存与官方升级

## 维护目标

保留自己的定制功能，同时可以跟进官方稳定版本。升级先在独立副本中试合并，说明冲突与行为影响，验证后再交付。当前保存的版本是定制源码快照，不代表报价或生成流程已经通过运行验收。

## 仓库与分支

- `upstream`：作者的 `glanderness/BeefTV` 仓库，只用于读取官方更新。
- `origin`：自己的 GitHub 私有仓库，用于异地保存源码。
- `main`：当前采用的官方基线为 `v1.7.15`（`bb8d5b83a791a617ca5add41a6874749ed911add`），不加入定制修改。首次定制基线为 `v1.6.22`。
- `atlas-cost`：自己的定制版，包括报价、模型选择与能力适配、网络连接处理及相邻测试。日常修改保存在这个分支。

源码提交只保护已提交的文件；后续改动也需要提交并推送。软件数据、素材、数据库、密钥和编译好的程序不属于源码备份。跨版本升级还需要单独保护使用数据。

## 已有定制的检查清单

1. 报价接口 `/api/workspace/model-cost`、前端报价显示、缓存与素材报价处理。
2. 模型菜单的渠道、系列、版本、用途、搜索和可用性排序。
3. 图片参考限制、视频时长和音频生视频能力的适配。
4. 外部模型请求的多地址连接处理，保留已有地址校验。
5. 对应测试、类型、配置字段和 API 文档。

## 每次检查与升级

1. 查看本地分支、未提交修改和远程来源。先保存新的定制修改，不覆盖或清理工作区。
2. 读取官方更新，优先选定稳定版本标签；下载更新不等于替换当前软件。
3. 对比采用的官方基线与目标版本，列出双方修改重叠的文件、接口变化和数据库迁移。
4. 在独立临时克隆中，以已保存的定制提交建立升级分支，试合并目标标签。不要在日常工作区直接试合并。
5. 报告 Git 冲突、没有文本冲突但可能影响功能的变化，以及建议处理方式。逐段适配，不批量选择“全部用官方”或“全部用定制”。
6. 根据改动范围进行后端专项测试、前端专项测试和构建；检查上面的定制功能以及官方新增功能。运行真实模型生成可能产生费用，应遵守当前用户授权。
7. 软件替换前关闭相关程序并保存一致的数据备份；SQLite 如有 WAL 文件也需纳入备份，不能只复制正在写入的主数据库。
8. 验证通过后，才将验证过的升级提交纳入定制分支，将 `main` 前进到采用的官方版本，并推送。保留旧程序及对应数据备份；新版迁移过的数据库不能直接假定兼容旧程序。

## 给使用者的升级报告

- 当前版本、目标官方版本和主要更新。
- 定制功能受影响的位置与原因。
- 冲突及建议处理办法。
- 已验证的项目、未验证的项目与遗留问题。
- 是否已经替换软件，以及可恢复的程序和数据版本。

本流程不会自动定时检查或自动升级。需要时可以直接提出：“检查作者有没有更新，先告诉我合并风险。”

2026-10-11 的升级记录见 [v1.7.15 升级验证](upgrade-v1.7.15.md)。

原生节点拖出功能因影响普通拖动而撤回，见 [系统拖拽回退记录](drag-recovery-20261013.md)。后续升级应保留该撤回，直到实际客户端与其他软件共存时的拖拽验收完成。
